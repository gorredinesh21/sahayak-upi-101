🔍 What to notice

⚡ Steps 2–4 are the money legs

Between PSP → NPCI → payee bank, your account is debited and the payee's is credited. If ANY acknowledgement gets lost here, the payment shows "Pending" — this is the stuck zone.

🧾 Every hop writes a log

Each system stamps the transaction with its own reference + timestamp. Stacked together they form the audit trail — that's what "tracing" a payment means.

✅ The ✓ you see is the LAST message

Your app shows "Success" only after the final acknowledgement travels all the way back. Until then: spinner. The money may already be debited while you stare at that spinner.

03 · Message vs Money

Why "debit ho gaya, credit nahi" is even possible

The trick to understanding stuck payments: two different things move at two different speeds. The instructions fly instantly, the actual interbank settlement happens in periodic batches. Your bank balance is a ledger promise, not a truck of cash.

📨 Message lane — instant, per transaction

"Debit ₹2,800 from A""Debit done ✓""Credit ₹2,800 to B""Credit done ✓"

Each instruction + acknowledgement travels bank → NPCI → bank in under a second. Bank balances update off these messages immediately — that's why UPI feels instant.

💰 Money lane — batched, net settlement

🏦 Bank A owes ₹41,20,300 net⏰ settles in batches🏛️ to Bank B via RBI books

Behind the scenes, NPCI nets thousands of transactions between two banks and moves one net amount per settlement window. Customer-level, you never wait for this — your ledger entry is the promise.

🧠 The mental model that matters for Sahayak

"Debited but not credited" = the debit message succeeded, but somewhere on the credit path a message failed or got lost (response code Z5/Z9/Z6…). The system then owes you a reversal — NPCI rules push banks to auto-reverse by T+1 (usually within hours, worst case ~3 days). A stuck payment is really a broken promise with a legal deadline. That deadline is the agent's weapon.

The pattern to remember: clean codes (U30, Z2) = money never left, just retry. Dirty codes (Z5, Z8, U50) = debit done, credit failed → reversal owed. No code (T1/Pending) = nobody knows yet → status checks first. No code + success = wrong account, the scariest one.

07 · The Backtracking Playbook

Money is stuck. What do you check, in what order?

This is the exact order a human agent follows today (and what Sahayak automates). The discipline: establish facts before touching anything — status first, then trace, then timers, then escalate.

1

Read the status pair always first

App says what? (SUCCESS / PENDING / FAILURE) vs bank statement says what? (debited or not?). Four combinations, each pointing at a different scene. A FAILURE + debited statement = reversal owed, full stop.

2

Grab the trace kit RRN + amount + timestamp

RRN is the key every system can look up. Without it nobody can trace anything. This is why the agent collects it into the case file before acting.

3

Query down the chain status APIs

Ask PSP → NPCI → beneficiary bank: "did you see RRN …155?" The first one that says "no" marks the broken leg. The response code usually predicts this — the queries confirm it.

4

Start the reversal clock T+1 rule

Debited-but-failed payments must auto-reverse by T+1 (usually within hours; ~3 days worst case). If the clock has run out — that's a genuine grievance, escalate instead of waiting.

5

File once, then chase complaint discipline

Complaint with the PSP (Paytm 24×7) with RRN attached → they route to the bank → NPCI portal escalation if it stalls. One complaint, tracked with timers — not five angry duplicate tickets.

6

Last resorts only if ignored 30 days

Bank must resolve within 30 days; after that the RBI Ombudsman for digital payments takes the case. The existence of this ladder is why SLA timers matter — the agent knows when each rung unlocks.
