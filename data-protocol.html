Mode A
Debited, not credited

Reversal already flying from the rails — Sahayak verifies it and says it out loud before panic, then catches it if it stalls.

Mode B
SLA timed out

Pending past deadline — nothing self-heals. Sahayak files the complaint itself with the RRN and chases on timers.

Mode C
Fraud / wrong account

Debited AND credited — but to a fake or wrong account. The days-long complaining process, compressed to minutes by the agent.

03 · The Triage Layer

The router above the modes

The moment the customer presses the AI button — before they type anything — this layer runs. It fetches the stuck payment, reads the log columns, and pins the mode. The LLM never guesses which protocol it's in; the router decides, the agent executes. On the thinking-view, triage is row #1.

🔀 Press-the-button sequence
1 · Fetch candidates SQL

Customer's last 48h txns where status != 'SUCCESS' OR (SUCCESS with fraud signals) — plus any already-open case (→ resume it instead).

2 · Select the case

Exactly one candidate → attach silently. Multiple → quick-reply chips ("₹2,800 → shop@ybl · 14:02?"). None → the agent asks what happened; Gemini parses the reply (a claim like "galti se bhej diya" can open Mode C on a successful txn).

3 · Run the decision tree deterministic

Pure code on the columns below — no LLM, no tokens, no ambiguity. Output: {mode, reason}.

4 · Brief assembled with mode pinned to the LLM

The brief's first field is mode: "A" | "B" | "C" + the reason string. The LLM's system prompt says: "the mode is already decided — never re-triage, follow its protocol."

Python · router.py — the whole layer is one pure function
def triage(txn, rails, stats, user_claim=None):
    # rails = joined rows from psp/npci/remitter/beneficiary logs; stats = txn_history_stats
    if txn.status == 'FAILURE':
        if rails.debit_ts is None:
            return R('EXPLAIN', "declined before debit — nothing is stuck, explain + retry tip")
        if rails.reversal_credited_at:
            return R('A_DONE', "already back — confirm + receipt")
        if rails.reversal_initiated_at:
            return R('A', f"{rails.resp_code}: credit failed after debit, reversal in flight")
        return R('B', "debit done but no reversal started — file & chase")
    if txn.status == 'PENDING':
        if hours_since(txn.initiated_at) > SLA and rails.expiry_attempted:
            return R('B', "pending past SLA and the rails already gave up")
        return R('WATCH', "pending inside SLA — say it first, arm the timer")
    # status == SUCCESS:
    if stats.first_time_beneficiary and (
         txn.amount > 5*stats.avg_amount_30d or rails.ben.fraud_reports_count > 0
         or rails.ben.account_status != 'ACTIVE'):
        return R('C', "SUCCESS with fraud signature")
    if user_claim in ('wrong_account', 'fraud'):
        return R('C', f"customer claim: {user_claim}")
    return R('CLARIFY', "no stuck txn found — ask, then re-triage")
🌳 The full decision tree (every leaf is a routed outcome)
status = ?
FAILURE
debit_ts?
EXPLAIN — no debit, nothing stuck (quick tip + retry)
A_DONE — money already back (confirm + receipt)
A — reversal in flight → narrate + verify + catch stall
B — debit, no reversal → file & chase
PENDING
past SLA + expiry tried?
B — rails gave up → file & chase
WATCH — inside SLA → say it first + timer (A's sibling)
SUCCESS
fraud signature or claim?
C — fraud / wrong account → dossier + escalate
CLARIFY — ask the customer, then re-triage

Three leaves are the demo modes (A / B / C); the others keep the tree total: EXPLAIN, A_DONE and WATCH are Mode-A-family quick paths, CLARIFY hands the mic to the LLM for one question — then the router runs again on facts.

🧱 Why the router is code, not the LLM: the mode decision decides which money-rails apply — it must be auditable, instant (press-button latency), free (zero tokens), and unit-testable (feed it seeded logs → assert the mode). The LLM would be guessing from prose; the tree reads the same columns the protocols do. Determinism where the money is, intelligence inside the conversation — the same philosophy as the guardrails.
🎬 Demo payoff: the first thinking-view row is the router's verdict — "🧭 Triage → Mode A · Z5, debit present, reversal in flight" — followed by the agent's LLM turns. Judges see machine discipline first, intelligence second. That ordering IS the pitch.
04 · Mode A protocol

Mode A — "Your money is already coming back"

A

Debited, not credited — reversal in flight

Codes Z5 · Z8 · (Z9 with hold) — the rail owes a reversal by T+1; the crime is the silence around it
🎯 Detection (scheduler query on live tables)
SELECT t.txn_id, n.rrn, r.debit_ts, r.reversal_initiated_at
FROM   paytm_txn t
JOIN   npci_switch_log  n ON n.txn_id = t.txn_id
JOIN   remitter_bank_ledger r ON r.rrn = n.rrn
WHERE  t.status = 'FAILURE'
  AND  r.debit_ts IS NOT NULL                    -- money left
  AND  n.resp_code IN ('Z5','Z8')                -- credit leg broke
  AND  r.reversal_initiated_at IS NOT NULL       -- rail already returning

🧭 Protocol
Open with the answer message

Before the customer asks: Hindi/English WhatsApp + voice — "आपके ₹2,800 वापस आ रहे हैं" with RRN and the real ETA, not a generic 24–48h.

Verify the reversal is truly moving check_bank_status(rrn)

Read remitter_bank_ledger: reversal_initiated_at set? amount matches? hold_flag clear?

Most reversals land in hours. The timer exists for the ones that don't.

Confirm the landing message

When reversal_credited_at appears: "₹2,800 credited at 14:02 — receipt enclosed." Case closed, one thread, zero tickets.

If T+1 passes with no credit → escalate to Mode B protocol transition

The stall is exactly the case the rails never self-heal — file and chase (below).

On close, grow memory cognee.remember

Next Z5 at this bank gets a sharper ETA. 26h → 25.5h. Compounding honesty.

05 · Mode B protocol

Mode B — "Nothing will fix this by itself. So I did."

B

Pending past SLA — the zombie payment

Codes T1 · Z6 · U50 — auto-expiry already tried and failed; no rail will ever touch this txn again until a complaint is filed
🎯 Detection
SELECT t.txn_id, n.rrn, t.initiated_at, r.debit_ts, n.expiry_attempted
FROM   paytm_txn t
JOIN   npci_switch_log n ON n.txn_id = t.txn_id
LEFT JOIN remitter_bank_ledger r ON r.rrn = n.rrn
WHERE  t.status = 'PENDING'
  AND  now() - t.initiated_at > INTERVAL '30 minutes'   -- past first SLA
  AND  n.resp_code IN ('T1','Z6','U50')
  AND  n.expiry_attempted = true                      -- the rails gave up
📄 Case Brief fields (Mode B)
rrnamount_paiseinitiated_athours_pendingdebit_ts (nullable!)resp_codepsp latencyexpiry_attemptedreversal_owedexisting_complaint_idpreferred_lang

Two booleans decide everything: debit_ts (did money leave? if yes, a reversal is owed) and existing_complaint_id (never file twice — idempotency is a hard rail).

🧭 Protocol
Establish facts down the chain check_bank_status check_npci

Query remitter_bank_ledger then npci_switch_log: first system that says "unknown RRN" marks the broken leg — exactly the backtracking playbook, automated.

Confirm nothing self-heals check_npci

expiry_attempted=true + still PENDING = the case the rails abandoned. This check is what justifies acting, not waiting.

File the complaint — itself, now file_complaint(rrn, evidence)

Writes the complaints row with RRN + evidence bundle (timeline, codes, debit proof). Idempotent: second call for same RRN returns the existing complaint_id.

Arm the chase ladder set_sla_timer

T+1 nudge → T+3 escalation → 30-day ombudsman rung, tracked automatically. The ladder exists in code, not in anyone's memory.

Tell the customer what was DONE, not what to do message

"कंप्लेंट दर्ज हो गई (CMP-338821)। अगला अपडेट कल सुबह 9 बजे।" — the customer never navigates a helpline menu.

Every timer tick = a chase + an update chase message

Each beat visible in the thinking-view: query → status → notify. Until status flips to resolved and reversal_credited_at lands (if debit was owed).

06 · Mode C protocol

Mode C — "Every leg succeeded. That's the problem."

C

Fraud / wrong account — SUCCESS that shouldn't have happened

No error code exists — detection lives in relationship columns + the customer's own report. Today this takes days; the agent compresses it to minutes
🎯 Detection (post-success scan — the fraud net that catches what failure-dashboards can't)
SELECT t.txn_id, t.amount_paise, h.first_time_beneficiary,
       h.avg_amount_30d, b.fraud_reports_count, b.account_status
FROM   paytm_txn t
JOIN   txn_history_stats h ON h.user_id=t.user_id AND h.beneficiary_vpa=t.beneficiary_vpa
JOIN   beneficiary_bank_ledger b ON b.rrn = (SELECT rrn FROM npci_switch_log WHERE txn_id=t.txn_id)
WHERE  t.status = 'SUCCESS'                          -- the payment WORKED
  AND ( h.first_time_beneficiary = true
    AND ( t.amount_paise > 5 * h.avg_amount_30d      -- 5× their usual
       OR b.fraud_reports_count > 0                  -- VPA reputation
       OR b.account_status != 'ACTIVE' ) )            -- frozen / KYC-lapsed acct

Second trigger path: the customer reports it in chat — "गलत नंबर पर भेज दिया" / "fraud" — parsed by Gemini into {claim: "wrong_account"|"fraud", rrn?}, which opens a Mode C case on a SUCCESS txn.

📄 Case Brief = the evidence dossier (Mode C)
rrnamount_paiseamount_vs_avg_ratiofirst_time_beneficiarybeneficiary_vpa + fraud_reports_countaccount_statusdevice_id matchfull leg timeline (all SUCCESS)memory.vpa_linkskyc_tier

memory.vpa_links is Cognee's fraud graph: has this VPA appeared in prior cases, linked to mule clusters? Every closed case sharpens the net.

🧭 Protocol
REFUSE to auto-act — and say so hard rail

A successful payment cannot be un-made by an agent. The refusal is visible in the thinking-view — restraint as intelligence.

Assemble the complete dossier build_dossier(rrn)

All starred fields + the leg timeline + memory links, packaged once, so no human ever re-collects evidence.

File to the dispute desks file_complaint(type="dispute")

Wrong-account → remitter-bank dispute + beneficiary-bank hold request. Fraud → same + flag priority. The paperwork that used to take days, in seconds.

One alert, complete evidence escalate(dossier)

Risk desk gets one notification with everything attached. Humans decide; the agent prepared.

Guide the victim in real time message

Calm Hindi voice, step-by-step: what was filed, what the 1930 helpline / cybercrime portal steps are, what happens next. A victim who acts in minute 2 freezes money; day 3 doesn't.

Track the dispute like Mode B set_sla_timer

Follow-ups on the dispute's own SLA clock; customer informed at every state change until human resolution.

07 · Context strategy

"Feed the LLM all the logs" — yes, and here's the smart version

Your instinct is right that a bigger model changes what's possible. But big context is a luxury; targeted context is a discipline — raw log dumps cost tokens per turn, slow every decision, and bury the one line that matters. Our split gets both worlds:

💾 Layer 1 · Live data

Our SQLite — the seeded log tables above, open cases, complaints. The source of truth. Tools query it; nothing here goes to the LLM unfiltered.

📄 Layer 2 · The Case Brief

~18 selected fields + recent_events: the last 20 log events, one line each ("14:02:11 remitter debit ₹2,800 ✓", "14:02:13 NPCI credit leg FAIL Z5"). Fat enough to reason, thin enough to stay sharp — and rebuilt from Layer 1 at chat-open, before the customer types.

🧠 Layer 3 · Memory graph

Cognee over closed cases → ETAs, bank quirks, VPA fraud links. Injected into the brief as memory.* fields. Plus one tool for depth:

The tool that replaces log-dumping — the agent investigates visibly
get_log_slice(system="npci_switch_log", rrn="4102…155", range=(t0, t1))
# pulls ANY depth of raw log rows on demand — 50, 500, whatever the case needs.
# The LLM decides when it wants more evidence; the thinking-view shows the pull.
# Same total access, 1/10th the tokens, and it demos as investigation, not data-shoveling.
✅ Why this beats dumping all logs every turn: a 5-turn case × 50 raw log rows × every message = tokens rebilled 5 times for text the model already summarized; latency stacks; and the one decisive line (expiry_attempted=true) competes with noise. The 20-event tail answers 95% of cases; get_log_slice covers the rest — visibly.
08 · Data provenance

Where does the sandbox data come from?

Researched Oct 1. The honest answer has three parts: what's real and public, what can never be public, and how we calibrate our generator with the real numbers.

✅ Real & public — we use it

· Bank-wise BD/TD rates — NPCI's monthly per-bank decline statistics (via NPCI, Dataful, India Data Portal). Our sandbox's ten mock banks carry the real FY25 probabilities: HDFC 0.08% → Airtel/Jio Payments 7.2%+
· Official response-code semantics — NPCI's "UPI Error & Response Codes v2.3.1" and bank-published code lists anchor our Z5/Z9/T1 meanings
· System-wide mix — ~90% success / ~9% business declines / ~0.3–0.8% technical declines

🚫 Not public — and never will be

Individual transaction logs with RRNs, response codes, and all 5 legs exist only inside banks, PSPs, and NPCI — protected by RBI privacy rules and data-localization. No dataset, Kaggle or otherwise, legitimately contains them (the public "UPI transaction datasets" are simulated and lack RRN/codes). Any repo claiming real per-txn logs would be a leak, not a dataset.

🛠️ So our sandbox = calibrated synthetic + authored demo cases (BUILT & TESTED)

A Python seeder generates ~4,100 transactions for 40 users over 4 months — each failure a causally consistent story across all five log tables (which leg broke, when, with which code, whether the reversal fired and when it landed). Real-world rates drive every draw: per-bank TD probabilities from NPCI data, the BD/TD mix, log-normal amounts, fraud-VPA pool with report counts. On top: the demo user + 3 authored demo cases (₹2,800 Z5 · ₹1,150 T1 · ₹19,000 fraud-VPA) + closed look-alike cases so Cognee memory has food from day one. The triage router was run against all of it — 8/8 checks pass: demo cases → A/B/C, plus EXPLAIN / A_DONE / WATCH / CLARIFY edge leaves.

Why this is demo-honest: judges asking "is this data real?" get the best available answer — "the numbers are calibrated to NPCI's published per-bank rates; the transactions are synthetic because real per-transaction logs are legally impossible to obtain — here's the generator."
